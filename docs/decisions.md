# Decisions

One line per ambiguity resolved, with date and phase.

- 2026-10-26 · Phase 1 · The project root is this folder (`pyproject.toml` here, package in `hearth/`), instead of an extra `hearth/` wrapper folder.
- 2026-10-26 · Phase 1 · `Identity.create(path, passphrase, kdf)` generates *and saves* the identity (it needs a path to save to); `Identity.generate()` makes an unsaved one for tests.
- 2026-10-26 · Phase 1 · `debug sign` writes a `post` with a plaintext body `{"text": ...}`, and `validate_entry` accepts that post body until Phase 5 switches posts to `{"box": ...}` (marked `TODO(phase 5)`), matching Phase 4's plaintext posts.
- 2026-10-26 · Phase 1 · `debug sign` always produces entry #1 (no store until Phase 2) and self-checks it with the author as the only member, since no group exists yet.
- 2026-10-26 · Phase 1 · `validate_entry` takes the parsed dict, not an `Entry`, so it can report shape errors; `parse_entry(raw)` does strict parsing and the size check on raw bytes first.
- 2026-10-26 · Phase 1 · `group_create` is valid only as seq 1, with `author == admin == body.admin`; every other kind requires the author to be in `members` (the store will add the admin to `members` when it applies `group_create`).
- 2026-10-26 · Phase 1 · Field bounds: `seq` 1 to 2^31−1, `ts` 0 to 2^53−1, all hex lowercase; `sig` is 128 hex chars.
- 2026-10-26 · Phase 1 · Added two small debug helpers not named in the spec: `debug verify FILE --group HEX` (for the "poke it" experiments) and `debug sign --out FILE` (PowerShell's `>` re-encodes output as UTF-16, which would break the entry bytes).
- 2026-10-26 · Phase 1 · `init --kdf interactive|moderate` exists from Phase 1 (default `moderate`); tests use `interactive` for speed, and one test covers `moderate`.
- 2026-10-26 · Phase 1 · Passphrase files: one trailing newline is stripped; empty passphrases are refused; on POSIX any group/other permission bit is refused (so `0600` and `0400` pass). Windows has no POSIX bits, so no check there; protection comes from the user-profile ACLs.
- 2026-10-26 · Phase 1 · Profile names are limited to `[A-Za-z0-9_-]{1,32}` because they become folder names (blocks `--profile ../../x`).
- 2026-10-26 · Phase 1 · No `@property` (the decorator rule): `Identity.pubkey`, `encryption_pubkey` and `short_id` are plain dataclass fields filled in `__post_init__`. `Identity.__repr__` is overridden so private keys never reach a log line.
- 2026-10-26 · Phase 1 · `identity.key` plaintext is canonical JSON `{"v": 1, "signing_key": hex seed, "encryption_key": hex}`.
- 2026-10-26 · Phase 1 · A wrong passphrase and a corrupted key file give the same error (`wrong_passphrase`): SecretBox can't tell them apart, by design.
- 2026-10-26 · Phase 1 · The lock file `hearth.lock` is left on disk after exit; only the OS lock matters, and the OS drops it when the process dies. On Windows the lock covers byte 0.
- 2026-10-26 · Phase 1 · CI runs on Ubuntu and Windows (the owner develops on Windows), upgrades `pip` before installing, and runs `pip-audit --skip-editable` (the local `hearth` package isn't on PyPI).
- 2026-10-26 · Phase 2 · `debug create-group` moved from Phase 4 to Phase 2 (owner's choice), so `debug sign` can append real entries for `debug log` to show.
- 2026-10-26 · Phase 2 · `debug sign "text"` now appends to the profile's log (group taken from `meta`). Removed the Phase 1 flags `--group` and `--out`; `debug verify` now re-checks the whole store instead of a file.
- 2026-10-26 · Phase 2 · `validate_entry` is split into `validate_contents` (everything but chain position) and `check_chain`; `validate_entry` still runs both. The store marks a fork only for an entry that passes `validate_contents`, so garbage can never get an author flagged.
- 2026-10-26 · Phase 2 · A fork is either a different genuine entry at a seq we hold, or a genuine entry at head+1 whose `prev` doesn't match our head. A gap (seq > head+1) is a plain rejection.
- 2026-10-26 · Phase 2 · "Identical duplicate" means the same entry hash. The hash excludes `sig`, and Ed25519 signatures are deterministic, so this is the same entry.
- 2026-10-26 · Phase 2 · The store keeps accepting a forked author's later entries that fit its own chain; stopping sync with the peer that sent the fork is Phase 4's job.
- 2026-10-26 · Phase 2 · Membership is applied inside the append transaction: `group_create` adds the admin (`added_seq` 1), `member_add` adds the member (`added_seq` = the admin's entry seq). Re-adding keeps the first `added_seq`.
- 2026-10-26 · Phase 2 · `Store.create_group(raw)` takes `meta.group_id` and `meta.admin` from the `group_create` entry itself, after checking its signature and that author == `body.admin`, in one transaction.
- 2026-10-26 · Phase 2 · The full spec schema (including `chunks`, `outbox`, `invites`) is created now as schema version 1. A different version is refused with "delete the data directory" (no migrations before the MVP).
- 2026-10-26 · Phase 2 · `Store` takes an injectable `clock` (Unix ms) so tests control `sort_ts`; `now_ms()` moved to `entry.py`.
- 2026-10-26 · Phase 2 · `debug log` and `debug verify` open no key files, so they don't ask for a passphrase, but they still take the data-dir lock.
- 2026-10-26 · Phase 2 · SQL column lists are written out in full rather than formatted into strings, which keeps bandit's B608 quiet without `# nosec`.
- 2026-10-26 · Phase 2 · The CLI switches stderr to UTF-8 as well as stdout (a `…` in an error message crashed on the Windows code page).
- 2026-10-26 · Phase 3 · Pinning is optional while there are no invites: `run --dial H:P` alone dials unpinned (the spec's Phase 3 command has no key) and prints a warning; `--dial-pubkey HEX` pins, and `config.json`'s `home_host` + `home_pubkey` pin automatically once Phase 6 fills them.
- 2026-10-26 · Phase 3 · A HELLO claiming our own pubkey is refused. Both sides sign the same transcript, so otherwise someone could bounce our own AUTH back to us and pass as us.
- 2026-10-26 · Phase 3 · The pin is checked as soon as HELLO arrives, before we sign anything, rather than after AUTH.
- 2026-10-26 · Phase 3 · If the authorizer says no, the peer gets `ERROR not_member` and is closed; the home node's `LIMITED` state replaces this in Phase 6.
- 2026-10-26 · Phase 3 · `ERROR` is only sent once the encrypted session exists; handshake failures just close the connection.
- 2026-10-26 · Phase 3 · The first PING goes out as soon as a session is `ACTIVE` (then every 20 s), so a new connection proves itself at once. "Silence" for the 60 s idle timeout means no frame received at all.
- 2026-10-26 · Phase 3 · `run` listens only with `--listen`, or on `config.json`'s `listen` when `role` is `home`; member nodes don't listen otherwise. It dials `--dial`, or `config.json`'s `home_host` (stored as `host:port`).
- 2026-10-26 · Phase 3 · IPv4 only: listen addresses must be IPv4 literals, and dials use `AF_INET` (hostnames resolve at every dial).
- 2026-10-26 · Phase 3 · The 64-total / 8-per-IP connection limits apply to inbound connections and are built now, along with reconnect backoff. Backoff resets after any session that reached `ACTIVE`; each dial's TCP connect is bounded by the handshake timeout.
- 2026-10-26 · Phase 3 · `random` is used for backoff jitter and the banner tagline, marked `# nosec B311` (the spec allows it for these).
- 2026-10-26 · Phase 3 · Closing a connection waits for the socket at most `idle_timeout`, then aborts it, so a peer that stops reading can't pin a task.
- 2026-10-26 · Phase 3 · `make_node` is a pytest fixture: `await make_node(name, passphrase, **overrides)` (tmp_path filled in), defaulting to 0.5 s handshake/idle timeouts and 0.05 s ping/backoff. Timeout tests pass 0.05 s explicitly; 0.5 s keeps a busy Windows laptop from failing real handshakes.
- 2026-10-26 · Phase 3 · Untrusted strings in log lines go through `protocol.snippet()` (repr, cut to 40 chars), so a peer can't forge log lines with newlines. ERROR `msg` is capped at 500 characters.
- 2026-10-26 · Phase 3 · `run --verbose` turns on DEBUG for Hearth's own loggers only.
- 2026-10-26 · Phase 4 · `debug sign` is removed; `post` replaces it. New modules not in the spec's layout: `actions.py` (one implementation of each user operation, used by both the CLI and the control channel), `pending.py` (split from `sync.py` to keep it under 400 lines) and `cli.py` (commands split from `__main__.py`, which now only parses arguments).
- 2026-10-26 · Phase 4 · The control channel requires the token on POSIX too, not just Windows (stricter than the spec, and one request format everywhere). `control.token` holds `{"port": null | int, "token": hex}`. One request per connection; requests are capped at 256 KiB, replies at 8 MiB, 10 s timeout.
- 2026-10-26 · Phase 4 · `init` and `run` always work directly on the data dir; every other command goes over the control channel when the lock is held. A held lock with no control channel yet (node still starting) gives a clear "try again" error.
- 2026-10-26 · Phase 4 · ENTRIES replies are matched to WANTs in order (oldest first). A WANT with a bad range still gets an empty ENTRIES, so the asker's order stays in step.
- 2026-10-26 · Phase 4 · The 1.5 MiB ENTRIES budget is measured on each entry's JSON-escaped size, so the frame really stays under 2 MiB; a reply always carries at least one entry if there is one.
- 2026-10-26 · Phase 4 · An empty ENTRIES reply makes us forget that author's claim until the peer's next HEADS, so a peer that claims more than it has can't cause a request loop.
- 2026-10-26 · Phase 4 · An invalid entry, a fork, or a full pending queue during ENTRIES stops the batch and blocks that author with that peer for the rest of the session (the spec's fork rule, extended to bad entries for the same loop-avoiding reason). Authors with entries in the pending queue aren't re-requested from anyone until those entries are retried.
- 2026-10-26 · Phase 4 · The admin's log is always requested first, since everyone else's membership lives in it.
- 2026-10-26 · Phase 4 · We send at most 90 WANTs per 60 s to one peer (`WANT_SEND_LIMIT`); peers accept 100. Hitting our own pace schedules a retry rather than breaking the peer's limit. A peer that breaks ours gets `ERROR rate_limited` and is closed.
- 2026-10-26 · Phase 4 · HEADS aren't signed, so a member could lie in HEADS and get an honest author marked forked. Accepted: the MVP threat model trusts members, and non-members can't reach ACTIVE from Phase 6 on.
- 2026-10-26 · Phase 4 · Pending retries repeat until a pass stores nothing (a `member_add` can itself be pending behind the admin's `group_create`). Anything that fails for a reason other than "not a member" is dropped; normal sync fetches it again if needed.
- 2026-10-26 · Phase 4 · Peers' HEADS are kept even before we're in a group; `debug join-group` on a running node immediately re-checks them. The periodic HEADS loop also re-requests anything missing and evicts expired pending entries.
- 2026-10-26 · Phase 4 · `feed` shows the newest 20 posts by default (max 100), ordered by `sort_ts DESC, author, seq`; Phase 7 adds cursor pagination.
- 2026-10-26 · Phase 4 · The pending queue's 4 MiB cap counts UTF-8 bytes, not characters.
- 2026-10-26 · Phase 4 · `run` on a busy listen port prints a clear error instead of a traceback.
- 2026-10-26 · Phase 4 · Test helpers: `make_node(..., start=False)` builds without starting; `control=True` opens the control channel; `node.data_dir` is set for tests only.
- 2026-10-26 · Phase 5 · The schema version is now 2 because post bodies became encrypted boxes; Phase 4 databases are refused with "delete the data directory".
- 2026-10-26 · Phase 5 · Group setup (`create-group`, `debug join-group`, `debug show-group-key`) only runs with no node running on that data dir: it reads or writes key files with the passphrase, which a running node never keeps.
- 2026-10-26 · Phase 5 · Until Phase 6's invites, a member gets the group key by hand: the admin runs `debug show-group-key`, and the member pastes it at a hidden prompt (or uses `--group-key-file`) so it stays out of shell history. `group.key` uses the same KDF strength as `identity.key`.
- 2026-10-26 · Phase 5 · A member's home node is the ACTIVE peer whose pubkey is the group admin's. Only a node with `role: home` accepts CHUNK_PUSH, and only from members, with a matching hash, within quota. The home node's own image posts skip the outbox, and the home node never fetches chunks.
- 2026-10-26 · Phase 5 · An outbox post is signed when its last chunk is acknowledged, so its `ts` is upload time and it appears in feeds when it actually lands.
- 2026-10-26 · Phase 5 · On `quota_exceeded` (ERROR, then close, as the spec says for every ERROR) the poster stops pushing for 10 minutes (`OUTBOX_QUOTA_RETRY`); the post stays in the outbox and `feed` shows it as waiting.
- 2026-10-26 · Phase 5 · CHUNK_WANT has its own 100/min limit, separate from WANT's; the fetcher paces itself at 90/min. It asks for at most 4 chunks per request, shares one download per chunk ID, retries corrupted replies, fails at once on CHUNK_MISSING, and keeps the chunks it fetches (nodes never delete chunks).
- 2026-10-26 · Phase 5 · `post --image` sends absolute file paths over the control channel and the node reads the files (same user, token-protected). Size is checked before reading. A post may have empty text if it has an image, and an over-long post is refused before anything is queued.
- 2026-10-26 · Phase 5 · The store can't see inside boxes, so `feed.open_box()` validates post contents on every read; malformed posts show as unreadable. `feed.py` is started now (open and check posts); Phase 7 adds pagination and caching.
- 2026-10-26 · Phase 5 · The spec's availability test ("goes offline immediately after the post appears") is read as "after the post appears on the home node". Sync is pull-based, so an entry only leaves the poster's laptop once home has asked for it. What's being tested is that the *image* survives without its poster.
- 2026-10-26 · Phase 5 · Peer's `on_active` hook now runs after the handshake timeout window (it may upload an outbox), and Peer remembers the last ERROR code it received.
- 2026-10-26 · Phase 5 · `verify` moved from `store.py` to `actions.verify()` to keep `store.py` under 400 lines; `cli.py` was split into `cli.py` (one-shot commands) and `cli_setup.py` (init, run, group setup) for the same reason.
- 2026-10-26 · Phase 5 · Image types are JPEG, PNG, GIF and WebP (RIFF...WEBP) by magic bytes; SVG is never allowed (it can carry scripts). The control-channel reply cap is 16 MiB so `debug image` can return a 10 MiB image.
- 2026-10-26 · Phase 5 · Every phase now ends with the full suite on Linux under Python 3.12 (the CI target) in Docker, as well as on Windows. The laptop's Python 3.14 evaluates annotations lazily and hid a missing import that crashed on 3.12.
- 2026-10-26 · Phase 6 · The spec's invite retry ("same token, same pubkey after a lost INVITE_OK gets the stored INVITE_OK again") contradicts its own state table: by then the joiner is a member, so the home node sends HEADS first and the joiner, still in JOINING, closes. Owner's choice: drop retries. A token works once, for anyone. A joiner in JOINING that gets HEADS or PING closes with "ask for a new invite and join with a fresh profile". The sealed key is still stored with the invite, as the spec's step 3 says.
- 2026-10-26 · Phase 6 · Invite links get their host from `invite --host name:port`, or from a new optional `public_host` in `config.json` (the spec's `invite --expires 48h` has nowhere else to get it). A raw-IP host gets a printed nudge to use a hostname.
- 2026-10-26 · Phase 6 · The authorizer is `group.is_member` (the admin, or anyone in the membership table). LIMITED exists only on the home node (role `home`), the only node that takes invites. Any other node refuses unknown peers with `ERROR not_member`. Connection-layer tests opt into `network.allow_everyone`.
- 2026-10-26 · Phase 6 · Members talk only to the admin until they've synced, since a brand-new member knows no one else. The three-node test's relay node is therefore the admin/home node (the spec's "via the home node"), and a joiner posts only after its `member_add` has arrived.
- 2026-10-26 · Phase 6 · `join` creates an identity for a new profile (or reuses one from `init`), saves `home_host`/`home_pubkey` from the link so `run` needs no flags, waits up to 60 s for the history, then writes a profile entry (`--name`, default the profile name) and waits for home to fetch it. It only writes the profile once its own `member_add` has arrived.
- 2026-10-26 · Phase 6 · Profile entries hold `{"name": str}` (1 to 64 characters); `feed` and `status` show the latest readable name per author.
- 2026-10-26 · Phase 6 · Invite rate limiting counts every redemption attempt per remote IP (5 per 10 minutes) and answers the sixth with `ERROR rate_limited`.
- 2026-10-26 · Phase 6 · `debug join-group`, `debug show-group-key` and `debug add-member` were removed (replaced by invites, as planned); `actions.add_member` stays for tests.
- 2026-10-26 · Phase 6 · To stay under 400 lines per file: the handshake crypto and helpers moved to `session.py` (with `PeerClosed`), address/backoff/connection-limit plumbing to `network.py`, and the chunk/outbox/invite queries to `tables.py` (`store.chunk_table`, `store.outbox_table`, `store.invites`). `Store.redeem_invite` stays in `store.py` because it spans the invites and entries tables in one transaction.
- 2026-10-26 · Phase 6 · A joiner sees the home node's full ERROR text (escaped, up to 500 characters) rather than the 40-character log snippet, because it's shown to a person. The control channel now starts before listening, so "Listening on" means CLI commands work.
- 2026-10-27 · Phase 7 · The page's three files (`/`, `/app.js`, `/style.css`) are served without the token: the page has to load before it can read the token from its URL. Every `/api/` call needs it. The Host check applies to everything.
- 2026-10-27 · Phase 7 · The page's files carry `Cache-Control: no-cache` (found in the browser check: after an update the browser kept a stale stylesheet), and decrypted images carry `no-store` so they never sit in the browser's disk cache.
- 2026-10-27 · Phase 7 · Feed order is the tuple (sort_ts, author, seq) descending everywhere, and the cursor means "strictly older than". `Store.posts` used to sort author ascending within a sort_ts; it now matches the cursor so ties page cleanly. The limit is 1 to 100, default 50.
- 2026-10-27 · Phase 7 · `FeedCache` keeps up to 5,000 decrypted posts by entry hash (posts never change); display names aren't cached, so a new profile shows on the next poll.
- 2026-10-27 · Phase 7 · `app.js` redraws only when the feed changed, reuses the blob URLs of images still shown, and revokes the rest. That's the spec's "revoke old object URLs on re-render" without refetching every photo every 5 seconds.
- 2026-10-27 · Phase 7 · `POST /api/posts` needs a Content-Length of at most 45 MiB (browsers always send one) and streams the multipart body, capping each part (10 MiB per image, 40,000 bytes of text). Only `text` and `image` fields are accepted.
- 2026-10-27 · Phase 7 · API errors are JSON `{"error": ...}`: 401 token, 403 Host, 400 bad parameters, 404 no such image, 409 not in a group yet, 413 too big, 504 the image didn't arrive within 30 s.
- 2026-10-27 · Phase 7 · "Last sync time" in `/api/status` is when this node last received HEADS or ENTRIES from anyone.
- 2026-10-27 · Phase 7 · `run --web-port` overrides `web_port` from `config.json` (a second profile on the same laptop needs its own port), and `run --headless` skips the UI. The CLI's own test processes run headless.
- 2026-10-27 · Phase 7 · `actions.post` reads files and hands bytes to `post_with_images`, which the web API calls directly, so both doorways share one implementation. `log` and `verify` moved to `audit.py` to keep `actions.py` under 400 lines.
- 2026-10-27 · Phase 7 · The token stays in the page's URL (not cookies, not storage), so a reload keeps working; `Referrer-Policy: no-referrer` stops it leaking to other sites. A page opened without it says to use the printed link.
- 2026-10-27 · Phase 8 · `run --role home|member` overrides `config.json` and is saved there. Otherwise a one-shot command run with the service stopped would still think the profile is a member (and, for one, queue its photos for a home node that is itself). `--role home` is refused for a profile that isn't the group's admin. `--role home` doesn't imply `--headless`; the unit passes both.
- 2026-10-27 · Phase 8 · Image posts written while a profile was still a member wait in its outbox for a home node. When that profile starts with `--role home`, its node signs them into the log at start: their chunks are already on its disk. Found in a hand test: they were stuck forever.
- 2026-10-27 · Phase 8 · `backup --out FILE` writes one uncompressed `.tar` (the chunks are encrypted, so they don't compress). Its layout is the data dir's own, so `tar -xf FILE -C <empty dir>` restores it. It holds an allowlist: the snapshot as `hearth.db`, `identity.key`, `group.key`, `config.json`, and files under `chunks/` shaped like chunks. The passphrase can't get in, wherever it's kept. The archive is created mode 0600 and named into place only when finished. An existing file is never overwritten (dated names for nightly runs).
- 2026-10-27 · Phase 8 · `backup` is split between two processes. The lock holder (the running node over the control channel, or the CLI itself) makes the database snapshot with `sqlite3.Connection.backup()` into `<data-dir>/backup-<random>.db`. The CLI then writes the archive and deletes the snapshot. The node never writes outside its data dir, so systemd's `ProtectSystem=strict`, `ProtectHome` and `PrivateTmp` can't send a backup somewhere the owner can't see. A multi-GB archive never blocks the node's event loop. Key files and chunks are copied as plain files: key files only change with no node running, and chunks are written once, before the database row that lists them.
- 2026-10-27 · Phase 8 · `debug verify` also re-hashes every image chunk the database lists (missing or damaged), but only with no node running: on a large home node that can take minutes, longer than the 10-second control channel.
- 2026-10-27 · Phase 8 · `run` stops cleanly on SIGTERM (POSIX), which is what `systemctl stop` sends. The finally blocks run, connections close and the control socket is removed. stdout is line-buffered, so the banner reaches the journal at once.
- 2026-10-27 · Phase 8 · On POSIX, commands refuse a data dir owned by another user ("run this as that user: sudo -u hearth ..."). A plain `sudo` against `/var/lib/hearth` could leave root-owned files the service can't open.
- 2026-10-27 · Phase 8 · The unit adds `StateDirectoryMode=0700` and `UMask=0077` to the spec's list, plus standard extra sandboxing: kernel tunables, modules, logs, clock, hostname and cgroups protected, `ProtectProc=invisible`, `RestrictNamespaces`, `RestrictRealtime`, `RestrictSUIDSGID`, `LockPersonality`, `SystemCallFilter=@system-service`. `systemd-analyze security` goes from 5.0 (MEDIUM) to 1.5 (OK). `MemoryDenyWriteExecute=yes` works with Python 3.12 and PyNaCl. All tested under systemd 255 in an Ubuntu 24.04 container.
- 2026-10-27 · Phase 8 · `deploy.md` creates `/var/lib/hearth` by hand (`install -d -o hearth -m 0700`) before `init`, since `StateDirectory=` only creates it when the service first starts. It writes the passphrase file before `init` and generates the passphrase at random (into the owner's password manager), so the service's file and the key files can't disagree.
- 2026-10-27 · Phase 8 · WireGuard fallback (as the spec requires): DNAT on the VPS without MASQUERADE, so friends' own IPs reach the home node. Otherwise the 8-connections-per-IP and 5-invites-per-IP limits would apply to the whole group at once. On the VM, `Table = off` with `ip rule from 10.77.0.2 table 7777` sends only replies to tunnelled connections back up the tunnel, and `AllowedIPs = 0.0.0.0/0` lets packets from any friend's address in. Tested in containers. Without the rule, new connections fail.
- 2026-10-27 · Phase 8 · Argon2id stays `moderate` for the home node on the evidence so far: 0.57 s per key file on the owner's laptop, 0.73 s in the Ubuntu container, 282 MiB peak at start. `debug bench-kdf` measures it on the VM itself; switch to `--kdf interactive` only if it shows a start above about 10 s or the VM can't spare 256 MiB, and note the numbers in phase-8.md.
- 2026-10-27 · Phase 8 · Found while testing: `status` with no node running crashed (it needed the identity for "you …" but didn't load it). It now loads it, still with one passphrase prompt. The invite rate limiter moved to `network.AttemptLimiter`, and the `run` tests to `tests/test_cli_run.py`, keeping files under 400 lines.
- 2026-10-29 · Phase 8 · The owner's VM is reachable only through Tailscale, and friends shouldn't have to install it. The home node can now sit behind Tailscale Funnel (deploy.md, path C), which the spec doesn't cover. The core design is unchanged: friends only ever dial out, to the one address in their invite link.
- 2026-10-29 · Phase 8 · An address may be `tls://host:port`: in `--host`, `--dial`, `public_host`, a member's `home_host`, and the invite link's `h=` (`h=tls://hearth-vm.tail1234.ts.net:443`). This extends the spec's link format. One string per address, so the TLS flag can't drift from the host it belongs to. Plain `host:port` links work exactly as before.
- 2026-10-29 · Phase 8 · The TLS wrapper doesn't check the certificate. The invite link pins the home node's key and Hearth's handshake inside refuses anyone else, so TLS here is only the envelope Funnel requires. Checking would add ways to fail (Python on macOS without a CA bundle, a skewed clock) and no safety. Python's `ssl` module, no new dependency; TLS 1.2 at least; SNI is sent, since Funnel routes by it.
- 2026-10-29 · Phase 8 · `run --proxy-protocol` reads a PROXY v2 header (`tailscale funnel --proxy-protocol=2`) at the start of every inbound connection and uses the address in it for the per-IP limits, invites included, and the logs. Without it every friend arrives from 127.0.0.1, and the 8-per-IP limit would refuse the ninth friend online. Only v2 (a v1 header gets a clear error). LOCAL and unspecified headers mean "use the socket's address", as the PROXY spec says. A header is believed blindly, so `run` refuses `--proxy-protocol` unless it listens on a loopback address. It isn't saved in config.json: only `run` uses it, and the unit file passes it.
- 2026-10-29 · Phase 8 · PROXY and TLS code lives in a new `hearth/transport.py`, keeping `node.py` under 400 lines. Tests use a stand-in front door (TLS outside, PROXY v2 inside) with a self-signed test certificate committed in `tests/data/`: the standard library can't make certificates, and the certificate isn't secret, since nothing checks it.
- 2026-10-30 · Phase 8 · The owner's VM host sits on someone else's tailnet, whose admin would have to allow Funnel and whose tailnet name would become public. So the home node runs in a Multipass VM of its own, on its own VLAN. That VM joins the owner's tailnet, tagged `tag:hearth`, and runs Funnel itself. The other option, Funnel on the host forwarding into the VM, would need the other admin's permission and a Hearth change (`--proxy-protocol` trusting a non-loopback forwarder). No code changed; deploy.md has "Path C in a VM of its own".
- 2026-10-30 · Repository · The folder became a git repository. The spec moved to `docs/spec.md`, since a name with spaces and a dash is awkward in links. Line endings are normalised to LF in git by `.gitattributes`. CI gained macOS because the README claims it, and that was untested. - 2026-10-30 · Phase 8 · An oversized first frame whose 4 bytes are an HTTP method, `HTTP`, or a TLS record start is named instead of reported as "Frame too big". A caller like that gets one INFO line, because strangers do this all day once a name is public, and a WARNING per crawler would bury real problems. An address we dialled that does it is still a WARNING, and `join` says to ask for a corrected link rather than retry, since a person has to fix the address. Inside an established session the same bytes stay a WARNING. Nothing is lost by the quiet line: the connection is dropped after the same 4 bytes, and a real Hearth frame can't look like this, because these all exceed the 2 MiB limit.
